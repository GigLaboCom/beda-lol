# 04 — «Бортовой журнал»

**Публичная страница, где автор рубрики (и потом любой желающий) показывает, сколько времени уходит на код и сколько на маркетинг. При перекосе яхта кренится и набирает воду.**

## Зачем

Доказательство, что автор сам на борту. Build-in-public с визуальным языком, который мгновенно считывается: крен и вода в трюме понятнее любых графиков. Для рубрики — постоянный источник еженедельных постов («журнал, неделя 7»). Для аудитории — со временем шаблон, который можно завести себе.

## Механика

### Что учитывается

| Поле | Как попадает |
|---|---|
| Часы на код | вручную, раз в день или неделю |
| Часы на маркетинг | вручную |
| Коммиты | автоматически из GitHub |
| Публикации | вручную ссылкой или автоматически из RSS / API площадки |
| Пользователи / регистрации | вручную или из аналитики |
| Разговоры с людьми | вручную, счётчик |

### Визуализация

- **Крен:** угол наклона яхты = функция доли кода.

```
share = code_hours / (code_hours + marketing_hours)      // за скользящие 14 дней
heel  = clamp((share − 0.5) · 70°, −25°, 35°)            // 50/50 → ровно, 100% код → 35°
```

Крен на маркетинг тоже возможен (отрицательный угол) — честно показывает и обратный перекос.

- **Вода в трюме:** растёт на каждую неделю без новых пользователей или разговоров с людьми, уходит при появлении. Плоскость воды внутри корпуса (`clippingPlanes` по корпусу или просто полупрозрачный объём).
- **Записи журнала** — лента под сценой в стиле судового журнала: дата, моноширинный шрифт, короткие строки.

```
23.09  код 6ч · маркетинг 0ч · коммиты 14 · пост 0
       крен 31° на правый борт. вода прибывает.
       запись: «ещё одну фичу — и тогда напишу».
```

Последняя строка — самоирония автора, это и есть душа формата.

## Интеграции

- **GitHub.** Публичные события пользователя без токена — `GET /users/{user}/events`, лимит для неавторизованных запросов — 60 в час с одного IP, поэтому запрашивать на сервере и кешировать. Для точного подсчёта вклада за период нужен GraphQL API с токеном (`contributionsCollection`). Коммиты в приватные репозитории без токена не видны.
- **Публикации.** RSS блога, API площадок при наличии; иначе вручную.
- **Аналитика.** Большинство сервисов аналитики дают API; начать с ручного ввода раз в неделю.

## Использование в рубрике

- Еженедельный пост: скриншот яхты + три строки журнала + вывод недели. Это самый дешёвый регулярный формат из всех тактик.
- Контрастные недели: «неделя, когда я вообще не писал код» — яхта кренится в другую сторону, хорошая картинка.
- Итоги месяца: график крена во времени (линия), видно, как меняется поведение.

## Для аудитории (второй этап)

Любой может завести журнал для своего проекта: та же страница, свой адрес. Связь с трекером 03 — журнал показывает регулярность, которая нужна буквам Д и О.

## Данные

```
log_entry { id, yacht_id, date, code_hours, marketing_hours, commits, posts, users_delta, talks, note }
```

Крен и вода вычисляются из последних записей, не хранятся.

## Техническая реализация

- Сцена яхты с двумя параметрами на входе: `heel` (поворот всей группы `yacht` вокруг `x`) и `water` (высота плоскости воды внутри корпуса).
- Плавность: крен меняется не рывком, а через затухающее качание — те же формулы, что у букв (`θ(t) = θ_target(1 − e^(−λt) cos ωt)`), это визуально связывает тактики.
- Статичная версия страницы генерируется для превью ссылок.
- Первый этап — только для автора: без регистрации, данные в файле или простой таблице.

## Метрики

- Для автора: регулярность публикации журнала, отклик на еженедельные посты.
- Для аудитории (этап 2): число заведённых журналов и доля обновлявшихся хотя бы 4 недели подряд.

## Риски

- **Честность неудобна.** Показывать 0 часов маркетинга публично — это и есть смысл, но это требует решимости. Стоит договориться с собой заранее о правиле «публикую любую неделю».
- **Приватные данные.** Цифры пользователей и выручки не обязательно показывать; крен считается только из часов.
- **Ручной ввод бросают.** Минимизировать: одна форма на неделю, три числа.

## MVP → расширения

**MVP:** страница автора, ручной ввод раз в неделю, крен и вода, лента записей.
**Шаг 2:** GitHub-интеграция, график во времени.
**Шаг 3:** журналы для аудитории, связь с трекером 03.

## Трудоёмкость

MVP — 3–6 дней. Интеграции добавляют по 1–2 дня на каждую, основная сложность — кеширование и лимиты API.
