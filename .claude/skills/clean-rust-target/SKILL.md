# clean-rust-target

Reports and optionally clears the Rust build cache for the repo and its active git worktrees. Build caches commonly reach several GB and are cheap to regenerate — only the source tree is precious.

This repo (beda.lol) has **one Rust build cache**: the Cargo workspace is rooted at the repo (`Cargo.toml`, `members = ["apps/api"]`), so every crate — today only `beda-api` — builds into the shared `./target` at the repo root. `apps/api` has no `target/` of its own. `archive/` contains no Rust.

If `CARGO_TARGET_DIR` is set in the environment, cargo writes there instead of `./target`; check it first and measure/clean that path.

## Step 1 — Measure

Show the user where the space is before deleting anything.

```bash
echo "CARGO_TARGET_DIR=${CARGO_TARGET_DIR:-<unset>}"
du -sh target 2>/dev/null
# Per-profile breakdown (debug is usually the bulk: dev, clippy, tests, sqlx):
du -sh target/*/ 2>/dev/null
# Catch strays (e.g. someone ran cargo inside apps/api with a different layout):
find . -type d -name target -not -path '*/node_modules/*' -not -path './.git/*' -prune 2>/dev/null | while read -r d; do du -sh "$d" 2>/dev/null; done
# For each active worktree, repeat `du -sh <worktree>/target`:
git worktree list
```

Report each path and size as a single line. If a `target/` does not exist for a path, skip it silently. If nothing exists anywhere, say so and stop.

## Step 2 — Confirm before deleting

Removing `target/` forces a full rebuild on the next `cargo` invocation. Always confirm with the user before running step 3 unless they explicitly asked for a no-prompt clean ("just clean it", "wipe target", etc.).

Quote the total size in the confirmation, e.g. "About to delete 6.2 GB of build cache across 2 paths — proceed?".

Offer partial options when useful:

- `cargo clean --release` — only `target/release` (from `task check` / `nx run api:build`), keeps the debug cache that `task dev`, `task gate` and `task test` use.
- `cargo clean -p beda-api` — only the workspace crate's own artifacts; keeps compiled dependencies (fast rebuild).

## Step 3 — Clean

Prefer `cargo clean` because it removes exactly what cargo created. Run it once from the repo root (it covers the whole workspace):

```bash
cargo clean
```

Fall back to `rm -rf <path>/target` only if cargo is unavailable or the directory is a stray whose manifest no longer exists.

For each active worktree (only if it still exists and has a `Cargo.toml`), run `cargo clean` in that worktree's root. Stop any running `task dev` / `watchexec` in that checkout first — it would immediately start rebuilding.

## Step 4 — Verify

Re-run the `du -sh` from step 1 to confirm reclaimed space. Report the delta to the user as one line, e.g. "Reclaimed 6.2 GB (target now absent)".

## Notes

- Do not touch `~/.cargo` — the registry/git caches there are shared across all Rust projects and removing them slows down every future build. The same goes for installed tools there (`sqlx-cli`, `cargo-deny`, `watchexec`).
- Do not delete `Cargo.lock` or `.sqlx/` — both are committed source (`.sqlx/` is the sqlx offline query data regenerated by `task gen`, and image builds depend on it via `SQLX_OFFLINE=true`), not build output.
- `task gate` touches the crate roots and re-runs clippy on the debug cache anyway; after a clean, the first `task gate` / `task check` does a full dependency rebuild (a few minutes). Mention this if the user is mid-iteration.
- The Docker image (`apps/api/Dockerfile`) builds inside its own container with `cargo-chef` and never uses the host `target/`. Reclaiming Docker build cache (`docker builder prune`) is a separate action — offer it only if the user asks about disk space in general, and confirm separately.
- Never `rm -rf` a worktree path itself — that leaves git's worktree metadata stale. Use `git worktree remove` for worktree cleanup; this skill only touches `target/` directories.
